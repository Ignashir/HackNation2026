Misja AED: how we built a national AED list on dane.gov.pl

Our main ideas, what we found in the dane.gov.pl code, what we changed in its backend and frontend, what we built ourselves, and what is still limited. State as of 22 November 2026, on a local copy of the portal.

1The problem and the rule we designed around

AED data in Poland is scattered across city registers, OpenStreetMap, private lists and apps. It is incomplete and often unverified. The challenge asks for one open, national, current AED dataset on dane.gov.pl and a common data scope so that every holder publishes the same way.

The rule from the organisers and mentors: each provider publishes its own dataset and is solely accountable for it. Many providers may publish. dane.gov.pl collects their files as resources and aggregates them into one common list. Anyone-can-publish is not allowed.

The mentors also pointed out that the portal already has code that helps. We found it: the high-value-data (DGA) list, which the portal already builds from many institutions' files.

2Our approach

  • We are the third party, not the publisher. We define the standard, provide the tooling and aggregate open data. Providers (town halls, hospitals, companies) publish their own registers through their representative (pełnomocnik) accounts.
  • The portal enforces the standard, but only where a dataset opts in. A dataset is bound to a versioned standard; its files must conform or they are not published. Other datasets behave as before.
  • A generic mechanism, AED first. Nothing in the backend is AED-specific; AED v1.0 is the first standard loaded into it.
  • No AI inside the portal. The portal's mapping of columns is deterministic (names, synonyms, value patterns). AI-assisted conversion of messy files belongs to our external tool.
  • Merging is rule-based and transparent. Records become one device only on hard evidence. Everything else is flagged, never silently merged.
  • Reuse the portal's own patterns. The national list copies how the DGA list works; harvested feeds use the portal's existing versioned XML format.

Problems we hit while publishing the real city files by hand

  • Too many clicks and fields spread over hidden tabs.
  • Silent failure: Marki's file is mis-quoted, so every row was read as one column, yet the portal showed green ticks.
  • Maps not assigned automatically; Przemyśl's file (a GeoJSON point column) is rejected by the live portal.
  • Drafts are never processed, so a file can't be checked before it is published.

How the national list merges providers

Same device only on evidence:

  • same_as: a provider states that its row is another provider's REGON:aed_id, or shares an osm:node
  • same UDI-DI + serial number, or manufacturer + model + serial number
  • closer than 50 m only: flagged as a possible duplicate, not merged

Which value wins:

  • higher precedence by institution type: local and state government 30, private 20, other 10
  • on a tie, the newer last_verified; empty values never overwrite
  • disagreements in critical fields, or positions more than 25 m apart, go to the conflicts file

5Frontend changes

  • New page /pl/aed, “Krajowy wykaz AED”: totals, merge statistics, providers with their precedence, links to the four files and the API, map and table of the list.
  • A “Wykaz AED” menu item and a standard badge on dataset pages bound to a standard.
  • Built from the portal's existing Angular components and translation files (PL/EN).

6The data standard (AED 1.0)

One row per device, CSV in UTF-8. Required: aed_id (stable), lat, lon, name. Recommended (12): address parts, placement, indoor, access, opening hours, 24/7, status, pads and battery expiry, last verified. Optional (15): TERYT code, floor, cabinet and unlock method, device data from the UDI barcode, operator, contact, notes, same_as.

It is a standard Frictionless Table Schema, the format the portal already validates, with Polish and English descriptions, examples and accepted header synonyms. The merge rules live in the same file. The spreadsheet version (AED_wzorcowy_zakres_danych_v1.0.xlsx) is generated from it and adds a fill-in template with drop-down lists.

7Our own tooling

Data

  • Unified AED database (PostGIS) with field provenance and a change log.
  • Importers: OpenAEDMap, OSM, Warsaw city API, and the registers already on dane.gov.pl (matching only, never republished).
  • Exporter to the standard, filling same_as from matches.
  • Feed generator: writes a provider's XSD 1.14 feed so the provider registers it once and never uploads by hand again.

Apps

  • Map app: pins coloured by open now, closed or out of service, clustering, nearest available AED.
  • Mobile concept: an offline “nearest AED” finder, and “Skaner AED” for reporting a new, missing or broken AED with a photo. Reports wait for the provider's review and never change data directly.

8How a provider publishes

  1. The representative creates an AED dataset and selects the data standard “AED 1.0”.
  2. They upload the file, or register our generated feed once.
  3. The portal suggests the column mapping and checks the file. If it conforms, it is published and its map is set up. If not, it stays a draft and the “Data standard” tab says why.
  4. Each night the national list is rebuilt from every conforming register; the changes file shows what moved.

10Limitations

  • Licensing. 18,310 of the devices come from OpenStreetMap, licensed ODbL. dane.gov.pl only offers Creative Commons licences, so on the real portal the list would start with the providers' own data (about 50 AEDs today). The mechanism works; completeness depends on providers joining.
  • The portal patch needs the portal team's acceptance. It is small and additive, but it is a change to their code.
  • Local prototype. Runs on a local copy of the portal; the nightly schedule is triggered by hand there, and old list files are not cleaned up yet.
  • Not done yet: rejection reasons in the harvest report and email, a search filter by standard, tests in the portal's test suite, our AI-assisted converter, precedence per institution (only per institution type).
  • Accessibility (WCAG 2.2 AA) not audited yet; the map pins rely on colour.
  • Data quality stays with providers. One Marki AED was left out of the corrected file because its coordinates in the source point to Krosno.
