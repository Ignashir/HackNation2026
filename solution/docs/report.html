Misja AED: how we built a national AED list on dane.gov.pl

Our main ideas, what we found in the dane.gov.pl code, what we changed in its backend and frontend, what we built ourselves, and its limitations. State as of 22 November 2026, on a local copy of the portal.

1The problem and the rule we designed around

AED data in Poland is scattered across city registers, OpenStreetMap, private lists and apps. It is incomplete and often unverified. The challenge asks for one open, national, current AED dataset on dane.gov.pl and a common data scope so that every holder publishes the same way.

The rule from the organisers and mentors: each provider publishes its own dataset and is solely accountable for it. Many providers may publish. dane.gov.pl collects their files as resources and aggregates them into one common list. Anyone-can-publish is not allowed.

The mentors also pointed out that the portal already has code that helps. We found it: the high-value-data (DGA) list, which the portal already builds from many institutions' files.

2Our approach

  • We are the third party, not the publisher. We define the standard, provide the tooling and aggregate open data. Providers (town halls, hospitals, companies) publish their own registers through their representative (pełnomocnik) accounts.
  • The portal enforces the standard, but only where a dataset opts in. A dataset is bound to a versioned standard; its files must conform or they are not published. Other datasets behave as before.
  • A generic mechanism, AED first. Nothing in the backend is AED-specific; AED v1.0 is the first standard loaded into it.
  • No AI inside the portal. The portal's mapping of columns is deterministic (names, synonyms, value patterns). Turning messy files into the standard is the job of our external converter, which runs in the provider's browser.
  • Merging is rule-based and transparent. Records become one device only on hard evidence. Everything else is flagged, never silently merged.
  • Reuse the portal's own patterns. The national list copies how the DGA list works; harvested feeds use the portal's existing versioned XML format.

Problems we hit while publishing the real city files by hand

  • Too many clicks and fields spread over hidden tabs.
  • Silent failure: Marki's file is mis-quoted, so every row was read as one column, yet the portal showed green ticks.
  • Maps not assigned automatically; Przemyśl's file (a GeoJSON point column) is rejected by the live portal.
  • Drafts are never processed, so a file can't be checked before it is published.

How the national list merges providers

Same device only on evidence:

  • same_as: a provider states that its row is another provider's REGON:aed_id, or shares an osm:node
  • same UDI-DI + serial number, or manufacturer + model + serial number
  • closer than 50 m only: flagged as a possible duplicate, not merged

Which value wins:

  • higher precedence by institution type: local and state government 30, private 20, other 10
  • on a tie, the newer last_verified; empty values never overwrite
  • disagreements in critical fields, or positions more than 25 m apart, go to the conflicts file

5Frontend changes

  • New page /pl/aed, “Krajowy wykaz AED”, laid out like the portal's DGA list of protected data: the national list resource shown in the portal's own table (with search, filters and a map tab), view and download counts, download buttons and usage conditions. Below it: the changes, all-rows and conflicts files, the API, and the providers with their precedence.
  • A “Wykaz AED” menu item and a standard badge on dataset pages bound to a standard.
  • Built from the portal's existing Angular components and translation files (PL/EN).

6The data standard (AED 1.0)

One row per device, CSV in UTF-8. Required: aed_id (stable), lat, lon, name. Recommended (12): address parts, placement, indoor, access, opening hours, 24/7, status, pads and battery expiry, last verified. Optional (15): TERYT code, floor, cabinet and unlock method, device data from the UDI barcode, operator, contact, notes, same_as.

It is a standard Frictionless Table Schema, the format the portal already validates, with Polish and English descriptions, examples and accepted header synonyms. The merge rules live in the same file. The spreadsheet version (AED_wzorcowy_zakres_danych_v1.0.xlsx) is generated from it and adds a fill-in template with drop-down lists.

7Our own tooling

Converter (AEDane): any register in, a standard file out

A single HTML page for people without technical training. It runs entirely in the browser: no server, and the data never leaves the provider's computer. One step per screen, plain explanations and a preview of what will go into the file.

  1. Load CSV/TSV (UTF-8 or Windows-1250), XLSX, JSON, GeoJSON, XML, KML or GML. GML coordinates in the Polish PUWG 1992 and PUWG 2000 systems are converted to WGS 84.
  2. Match columns. For each of the 31 fields it proposes a column from its name and its contents (postcodes, coordinate ranges, dates, hours). Any choice can be changed, set to a fixed value, or for aed_id generated.
  3. Fix values. It splits full addresses and coordinate pairs, converts dates and Polish opening hours (pn-pt 7-19 → Mo-Fr 07:00-19:00), swaps reversed coordinates, and shows each change. Remaining errors can be corrected in place.
  4. Download a standard CSV and JSON, a problem report, a dataset description for dane.gov.pl, and a mapping file to reuse with the next update.

Data

  • Unified AED database (PostGIS) with field provenance and a change log.
  • Importers: OpenAEDMap, OSM, Warsaw city API, and the registers already on dane.gov.pl (matching only, never republished).
  • Exporter to the standard, filling same_as from matches.
  • Feed generator: writes a provider's XSD 1.14 feed so the provider registers it once and never uploads by hand again.

Apps

  • Map app: pins coloured by open now, closed or out of service, clustering, nearest available AED.
  • Mobile mock-up in mObywatel: see the next section.

8Mobile: AED in mObywatel (mock-up)

Most people in an emergency will not open a data portal. They have mObywatel, the government app, already on their phone. We built a clickable mock-up of mObywatel (its tabs Dokumenty, Usługi, Kod QR and Więcej, in light and dark mode) where only the AED features work. The emblem and wording are generic, not the official branding.

Najbliższy AED (finding)

  • A green pill in the app header shows the distance to the nearest available AED, on every tab.
  • The finder shows an arrow (compass corrected for magnetic declination in Poland), the distance, and what helps on site: placement, floor, access, how to open the cabinet, opening hours.
  • Works without signal: the phone keeps the AEDs of its area (about 40 × 20 km cells) and decides “open now” itself. The server only learns which cell the phone is in, never its position.
  • A “Zadzwoń 112” button and a short how-to-use-an-AED guide (the demo does not dial).

Skaner AED (reporting)

  • A citizen takes a photo at an AED. If a known AED is within 25–60 m, they confirm it or report a problem: locked, broken, missing or moved. Otherwise they describe a new AED.
  • Reports without signal wait on the phone and are sent later; “Twoje zgłoszenia” shows each one's state.
  • A report never changes data. It waits for the provider's review; the photo is evidence for the reviewer.

9How a provider publishes

  1. The representative creates an AED dataset and selects the data standard “AED 1.0”.
  2. If their register has other columns or another format, they run it through the converter.
  3. They upload the file, or register our generated feed once.
  4. The portal suggests the column mapping and checks the file. If it conforms, it is published and its map is set up. If not, it stays a draft and the “Data standard” tab says why.
  5. Each night the national list is rebuilt from every conforming register; the changes file shows what moved.

11Limitations

  • Licensing. 18,310 of the devices come from OpenStreetMap, licensed ODbL. dane.gov.pl only offers Creative Commons licences, so on the real portal the list starts with the providers' own data (about 50 AEDs today). The mechanism works; completeness depends on providers joining.
  • The portal patch requires the portal team's acceptance. It is small and additive, but it changes their code.
  • Local copy of the portal. Everything runs on a local installation; there the nightly build of the national list is started by hand.
  • Scope of the portal changes. The harvest report and email do not list why a harvested file was held; the dataset search has no filter by standard; the changes are not covered by the portal's test suite; provider precedence is set per institution type, not per institution.
  • Separate tools. The converter and the feed generator are separate: a provider converts a file first, then publishes it by upload or feed.
  • mObywatel is a mock-up. It runs on our own API and database, not on mObywatel or the national list, and does not dial 112.
  • Accessibility (WCAG 2.2 AA) was not audited; the map pins rely on colour.
  • Data quality stays with providers. One Marki AED was left out of the corrected file because its coordinates in the source point to Krosno.
